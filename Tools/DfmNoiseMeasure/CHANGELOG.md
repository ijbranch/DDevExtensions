### Added

- (2026-11-28) **`links` command and `Check-DfmLinks.ps1`: the link check is repeatable (1.1.0)** — `DfmNoiseMeasure.dpr`, `DfmNoiseMeasure.dproj`, `DfmLinkCheck.pas`, `Check-DfmLinks.ps1`, `Help.md`.  `links` checks every `Module.Component` link in today's text DFMs has a target ( looked for in the link's own repository first, then every repository; a link to the form's own root or one of its components is not counted ), and with history pairs runs the DFM Link Guard's own rule over every past save and says which losses are still lost.  `Check-DfmLinks.ps1` does it all with one command: export the history, list the DFMs git knows, run `links`.  Only files git knows are checked, because a build's copies of forms beside its DCUs ( GITLAKLib's `37.0\<platform>\<config>` ) could still declare a component deleted from the real form.  Exit code 3 when something is found; an unreadable past save ( DBiServer's garbled `main.dfm` of 2026-01-02 ) is listed but does not fail every later run.  The decisions are in RTL-only `DfmLinkCheck.pas` ( 9 tests in `TestDfmLinkCheckDUnitX`, red first, six conditions mutation-proved ).  A link to the form's own root ( `frmMain.grdA` ) is checked within the form; "value elsewhere" means exactly that value on another property, not the text anywhere ( a caption, or the start of a longer name, hid a loss still lost ).  An empty file list ( git failed ) or a missing history file is a failure, never an all clear: found by the review; the command was proved on a throwaway repository with one broken and one lost link ( both reported, exit 3 ).  **Why:** Ian asked for the one-off check of 2026-11-28 to be repeatable.  First runs: DBiWorkflow 788 links in 235 forms all resolve, 13 past losses none still lost; GITLAKLib 8 forms, no links between modules; GITLAKDB 57 forms with 18 links all resolve, gllSpell 8 and WinTrak 4 forms with none, and none of the three lost a link in its history.
- (2026-11-28) **DfmNoiseMeasure 1.0.0: measures the IDE noise in saved DFMs** — `DfmNoiseMeasure.dpr`, `DfmNoiseMeasure.dproj`, `DfmNoiseMeasure.Core.pas`, `Export-DfmHistory.py`, `Help.md`, `Findings-2026-11-28.md`.  `identity` proves the parser round-trips every text DFM under some folders byte for byte; `compare` sorts the differences between old/new pairs ( exported from git history by `Export-DfmHistory.py` ) into categories, known IDE noise apart.  **Why:** measure before deciding whether DDevExtensions needs a snapshot-and-merge filter like Cesar Romero's delphi-dfm-noise-filter.  First run over 3,179 DBiWorkflow pairs: 1% of DFM commits are noise-only, but one silent loss of 11 data-module bindings ( DBiPV, 2025-10-16 ) went unrepaired for a year ( `Findings-2026-11-28.md` ).  The core is tested by `TestDfmNoiseMeasureCoreDUnitX` in the DDevExtensions suite.
