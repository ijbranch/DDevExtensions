# DFM noise in the DBiWorkflow suite: measured 2026-11-28

Question: after DDevExtensions' three DFM cleaners ( `Explicit*`, `PixelsPerInch`, `TextHeight` ), how much IDE
noise still reaches our `.dfm` files, and is a snapshot-and-merge filter such as delphi-dfm-noise-filter worth
building?

Corpus: the 32 git repositories under `E:\DBiWorkflow Development`, every commit that modified a `.dfm`, 2025-06 to
2026-11: **3,179 old/new pairs** ( 2 binary, skipped ), **23,370 changes**.

## Round trip

`DfmNoiseMeasure identity` over 324 text DFMs ( DBiWorkflow, GITLAKLib, GITLAKDB, GITLAKMCP, the parser's test data ):
**324 byte-exact**, after two parser fixes this measurement found ( `CHANGELOG.md`, 2026-11-28 ).  Before the second
fix, 18 of 246 DBiWorkflow forms failed.

## Noise

| | Pairs | Changes |
|---|---:|---:|
| Pairs with any known IDE noise | 349 of 3,155 ( 11% ) | 871 of 23,370 ( 3.7% ) |
| Pairs whose ONLY changes are known noise | 31 ( 1% ) | |

By category ( pairs / changes ): Property order 88 / 301; TextHeight added 58 / 58, removed 109 / 109; PixelsPerInch
added 44 / 44, removed 28 / 28; Explicit\* added 25 / 128, removed 19 / 110; Child order 32 / 37; DesignSize 41 / 56.

The noise arrives in **batches**, not steadily: 67 of the 301 property reorders are one DBiCommonFiles commit
( 2026-09-20 ), 41 of the 44 `PixelsPerInch` additions are June 2025, and the `Explicit*` additions sit in 2025-11/12
and 2026-05.  The removals are mostly the cleaners stripping old lines.  Ordinary saves are close to clean.

Not noise, though large: 3,041 component type changes and 1,825 `Font.Name 'Segoe UI' -> 'Tahoma'` changes are
deliberate migrations; Geometry changes ( 442 pairs ) cluster around a ratio of 1.0, so they are edits rather than
DPI scaling.

## Lost links: the finding that matters

26 removals of a link to another module's component ( `DataSource = dmX.dsY` and the like ) in 12 pairs.  Today:

- **7 followed the target's deletion** ( `dmGQ.VIL1`, `dmS.DBWReg` no longer exist ): deliberate.
- **19 are referenced in the current file again**, restored or moved.
- **None is still lost.**

One of them is the case the filter's author describes: on **2025-10-16 DBiPV's `MainFrm.dfm` lost 11 bindings at once**
( `DataSource`, `DataSet`, `LookupTable` to `dmPVForm` ), and they were not put back until **2026-10-11** ( commit
`707122c`, "Fix main-form bindings" ): a broken form for almost a year, with nothing reported at save time.

Image links: 126 removals, many followed by re-adds or by image lists being replaced; not examined one by one.

## Conclusion

- A full snapshot-and-merge filter is **not justified** by the noise: 1% of DFM commits are noise-only, and most noise
  comes in batches a reviewer sees at once.
- A **link-loss guard is justified**: one silent loss cost a year.  The candidate is a small DDevExtensions feature that,
  after the IDE saves a form, compares the file with the version it replaced ( `DfmNoiseMeasure.Core.CompareDfmText` )
  and reports in Messages any `Module.Component` link removed while that component still exists.  Not built: a
  design decision for Ian.
